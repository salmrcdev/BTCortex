# BTCortex security model

This document lists what BTCortex protects, where its trust boundaries are, the threats considered and the controls in place. Controls marked _planned_ are not implemented yet.

## Assets

| Asset                                                        | Why it matters                                 |
| ------------------------------------------------------------ | ---------------------------------------------- |
| Funds controlled by wallets connected to managed nodes       | Loss or theft is irreversible                  |
| Wallet files and descriptors in node data directories        | May contain keys; their loss can lose funds    |
| RPC credentials (cookies, passwords, `rpcauth`)              | Full control of a node and its wallets         |
| Blockchain data and indexes                                  | Expensive to rebuild (days of synchronisation) |
| Privacy: addresses, transactions, peer addresses, IP address | Linking a user to their coins                  |
| Integrity of installed software                              | A tampered binary can steal everything above   |

BTCortex never asks for, stores or transmits seed phrases (specification section 8.2). It holds no private keys.

## Trust boundaries

1. **WebView ↔ native shell.** The WebView is treated as less trusted: it renders remote-influenced data (node warnings, peer user agents). It has no shell, file-system or process permissions (`src-tauri/capabilities/main-window.json`) and a strict Content Security Policy (`script-src 'self'`, no remote connections). Its only privileged entry point is `orchestrator_call`.
2. **Native shell ↔ orchestrator.** Private stdio pipes between processes the shell started. The shell stamps the request origin; the orchestrator enforces per-method access (`ui` or `shell`).
3. **Orchestrator ↔ services on this computer.** Nodes over loopback RPC with their cookie (or, for a node found here whose `bitcoin.conf` sets a password, that password, read only with the user's consent); tor through its control port with its cookie; Fulcrum's ports bound to loopback.
4. **Orchestrator ↔ services on other computers that the user added.** Nodes over RPC with a user name and password (kept with DPAPI); LND with a macaroon, over TLS with its own `tls.cert` pinned; BTCPay Server with an API key created with the read-only permissions BTCortex requests (the permissions of a key pasted in are not checked); Electrum servers and block explorers, which take no credentials. Plain TCP or HTTP is used only with hosts on the local network or with onion addresses through BTCortex's tor; anywhere else TLS is required, with a publicly trusted certificate, LND's pinned certificate, or, for Electrum servers, one the user accepted and BTCortex pinned. Each service learns what it is asked: an explorer the chain tip and block hashes, and the pages the user opens there; an Electrum server the addresses looked up through it; a service on the internet also this computer's IP address, unless it is reached through Tor.
5. **BTCortex ↔ the internet.** Besides the services above and the nodes' own peer-to-peer traffic, BTCortex contacts the internet only to check for and download releases, their signatures and the keys that sign them, over HTTPS (every artefact is verified before use), and when the user probes an endpoint in the developer tools, which connects to the host and port the user typed, directly or through Tor, in plain TCP or HTTP unless TLS is chosen.

## Threats and controls

| Threat                                                                | Control                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | State                                                                                                   |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| A malicious or compromised download                                   | Builder signatures from at least 3 different people (keys that share a fingerprint or an e-mail address count as one person) over SHA256SUMS, streaming SHA-256 of the archive, version pinned in the file name, Authenticode check; nothing installed unless all pass                                                                                                                                                                                                                                       | Implemented, tested against the real 31.1 release                                                       |
| Following another chain by mistake                                    | Bitcoin Knots (whose releases since 29.4.1 follow a chain Bitcoin Core rejects) is set up only after the user agrees to that; its runtimes and data folders are its own and its configuration says so; a node is never moved between Knots and Bitcoin Core; Knots releases need the maintainer's signature besides the threshold and, being unsigned for Windows, must report themselves as Knots of the expected version before use                                                                        | Implemented, tested against the real 29.4.2 release                                                     |
| Trust-anchor substitution                                             | Builder keys bundled at a recorded `guix.sigs` commit; never added at run time; changes reviewed through `keys/bitcoin-core/manifest.json`                                                                                                                                                                                                                                                                                                                                                                   | Implemented                                                                                             |
| Archive attacks (path traversal, symbolic links, zip bombs, ADS)      | Entry-name validation, symlink rejection, total-size limit, `wx` writes into a fresh staging directory                                                                                                                                                                                                                                                                                                                                                                                                       | Implemented, tested                                                                                     |
| Withdrawn or insecure releases                                        | `30.0` and `30.1` refused; release candidates never installed automatically                                                                                                                                                                                                                                                                                                                                                                                                                                  | Implemented                                                                                             |
| WebView compromise reaching privileged functions                      | No plugin permissions beyond dialogs, notifications and opening HTTPS links; origin-checked method registry; shell-only methods unreachable; besides `orchestrator_call`, the WebView can reach only the shell commands that read and change BTCortex’s own start-up and closing preferences                                                                                                                                                                                                                 | Implemented, tested                                                                                     |
| Command injection                                                     | Processes spawned with argument arrays and `shell: false`; PowerShell inputs passed through environment variables as JSON, never interpolated                                                                                                                                                                                                                                                                                                                                                                | Implemented                                                                                             |
| Secret disclosure in logs and diagnostics                             | Redaction of sensitive keys and secret-looking values (extended private keys, cookies, Basic/Bearer headers, URL credentials, macaroons) before anything is written                                                                                                                                                                                                                                                                                                                                          | Implemented, tested                                                                                     |
| Secrets at rest                                                       | DPAPI (current user, application entropy) for stored secrets; cookie authentication avoids storing node secrets                                                                                                                                                                                                                                                                                                                                                                                              | Implemented, tested                                                                                     |
| Secrets in WebView storage                                            | Only theme and sidebar preferences are stored there                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Implemented                                                                                             |
| Private keys through the RPC console                                  | The console refuses methods that take or return private keys or wallet passphrases, including the legacy-wallet methods of Bitcoin Knots and of Bitcoin Core before 30 (`dumpprivkey`, `dumpmasterprivkey`, `dumpwallet`, `importprivkey`, `importmulti`, `sethdseed`, `sweepprivkeys`), and `listdescriptors` or `gethdkeys` asked for private keys; methods not in its catalogue are treated as dangerous and secret; every method in the help of Bitcoin Core 31.1 and Bitcoin Knots 29.4.2 is classified | Implemented, tested                                                                                     |
| RPC exposed to the network                                            | Managed nodes bind RPC to loopback (Bitcoin Core default); the configuration validator warns about non-loopback `rpcbind`/`rpcallowip`, `rest=1` and command-executing options                                                                                                                                                                                                                                                                                                                               | Implemented                                                                                             |
| Accidental mainnet operations                                         | `chain=` pinned in managed configurations; every check compares the node's chain with its profile; test networks are visually distinct                                                                                                                                                                                                                                                                                                                                                                       | Implemented, tested                                                                                     |
| Destructive operations by mistake                                     | Confirmation dialogues name the node and network before it is stopped, restarted or removed, and the orchestrator refuses a dangerous action unless the call carries `confirmed: true`, which the interface sends only from such a dialogue; removing a node never deletes data; managed nodes must be stopped first                                                                                                                                                                                         | Implemented for stop, restart, remove and peer bans                                                     |
| Two managers controlling one node                                     | Single-instance application, orchestrator lock file, data directory uniqueness per network in the database                                                                                                                                                                                                                                                                                                                                                                                                   | Implemented                                                                                             |

| An impostor answering at a Lightning node's address                   | LND's certificate pinned by its SHA-256 fingerprint; any other certificate is refused before anything, the macaroon included, is sent                                                                                                                                                                                                                                                                                                                                                                        | Implemented, tested                                                                                     |
| Payment secrets reaching the interface                                | Preimages and payment addresses are dropped by the orchestrator's parsers                                                                                                                                                                                                                                                                                                                                                                                                                                    | Implemented, tested                                                                                     |
| A forged LND release                                                  | Signatures from at least 5 of the 16 keys LND's `verify-install.sh` lists, each key counted once, over the manifest; archive hash; version check before activation                                                                                                                                                                                                                                                                                                                                           | Implemented, tested against the real 0.21.4 release                                                     |
| Keys or credentials in a backup that leaves the computer              | Wallets and credentials go only into backups encrypted with AES-256-GCM under a key from the user's passphrase (scrypt, N = 2^17); unencrypted backups leave them out and mask passwords in bitcoin.conf                                                                                                                                                                                                                                                                                                     | Implemented, tested                                                                                     |
| A tampered or damaged backup restored                                 | Every file's stored and original SHA-256 in the manifest, checked before use; GCM authentication; manifest paths confined to the backup folder                                                                                                                                                                                                                                                                                                                                                               | Implemented, tested                                                                                     |
| An inconsistent wallet copy                                           | Wallets are copied by Bitcoin Core (`backupwallet`) and restored by it (`restorewallet`), never copied while open                                                                                                                                                                                                                                                                                                                                                                                            | Implemented, tested against real bitcoind 31.1                                                          |
| Retention deleting the wrong folder                                   | Only folders directly in the backup folder with a valid BTCortex manifest are counted or deleted                                                                                                                                                                                                                                                                                                                                                                                                             | Implemented, tested                                                                                     |
| Security-relevant node settings changed behind the user's back        | Settings that expose a node, run commands, hold credentials or change how it connects are compared every 30 seconds for every node with files on this computer; a change made outside BTCortex raises a warning and a Windows notification; only HMAC-SHA256 digests under a key in the DPAPI vault are stored, never the values                                                                                                                                                                             | Implemented, tested                                                                                     |
| A payment server key that could spend or change a store               | Only read-only permissions are requested, through BTCPay's own key form; the key is tested before it is kept, stored only in the DPAPI vault, sent only over verified HTTPS, on the local network or through Tor, and never returned to the interface                                                                                                                                                                                                                                                        | Implemented, tested against a stand-in server                                                           |
| A transaction sent by mistake                                         | Sending needs `confirmed: true` in its parameters (risk `dangerous`); offered only when the node's mempool would accept the transaction, after a dialogue naming the network, node, value, fee and that it cannot be taken back; Bitcoin Core's limit on absurd fees stays in force                                                                                                                                                                                                                          | Implemented, tested against real bitcoind 31.1                                                          |
| A service on another computer read over an unauthenticated connection | Plain TCP or HTTP only with hosts on the local network (loopback, private and link-local ranges, carrier-grade NAT, `.local` names) or with onion addresses through BTCortex's tor; TLS anywhere else. The developer tools' endpoint probe is the exception: it connects where the user asks, and says so                                                                                                                                                                                                    | Implemented, unit-tested                                                                                |
| A service on another computer learning what the user looks up         | Explorers are asked only for the chain tip and block hashes until the user opens a page there; an Electrum server on another computer added for a node answers its address lookups only while the node's own Electrum server is not ready (none set up, still indexing, stopped or failed), and the address view names the server that learnt the address; services can be reached through Tor                                                                                                               | Implemented                                                                                             |
| A payment link acting by itself                                       | Reading a `bitcoin:` URI only explains it: nothing is paid, signed or sent, and proof-of-payment callbacks are never opened                                                                                                                                                                                                                                                                                                                                                                                  | Implemented, tested                                                                                     |
| A formula planted in an exported spreadsheet                          | Exported CSV fields that start with `=`, `+`, `-` or `@` are written as text                                                                                                                                                                                                                                                                                                                                                                                                                                 | Implemented, tested                                                                                     |
| Unknown TLS certificates                                              | Never accepted silently: an Electrum server's certificate that no authority vouches for is shown (subject, issuer, validity, SHA-256 fingerprint) and accepted only when the user ticks that it is their server's; it is then pinned and checked before every request, and a changed certificate is refused and raises a critical alert at once. LND's certificate is pinned from its `tls.cert`. BTCortex has no SSH, so there are no host keys to accept                                                   | Implemented for Electrum servers and LND, tested against stand-in servers with self-signed certificates |
| Firewall changes                                                      | BTCortex opens no firewall ports; `listen=0` avoids prompts                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Implemented (by omission)                                                                               |

## Limits of the protection

- DPAPI protects against other Windows accounts and offline disk theft, not against malware running as the same user.
- A pruned node cannot serve historical blocks; this is a privacy and capability trade-off explained to the user before set-up.
- Authenticode is defence in depth only; the certificate may legitimately change between releases.
