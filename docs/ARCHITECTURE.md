# BTCortex architecture

BTCortex is a native Windows desktop application that installs, configures, connects and monitors the self-hosted Bitcoin ecosystem. This document describes the architecture as it is implemented today and records the decisions behind it. The implementation state of every feature is tracked in [`IMPLEMENTATION_STATUS.md`](IMPLEMENTATION_STATUS.md).

## Principles

1. **Zero-touch for end users.** The user launches BTCortex and approves one recommended plan; the application downloads, verifies, installs, configures, interconnects and starts the components itself, with hardware-aware defaults. Native Windows components are preferred; WSL2 and Docker are used only where unavoidable.
2. **Security over convenience.** Privileged work never happens in the WebView. Secrets never reach the WebView, the logs or exports. Downloads are verified before use. Dangerous operations need explicit confirmation.
3. **Honesty.** The interface shows only real data with its source and freshness. A feature is presented as working only when it is implemented and tested.
4. **TypeScript first.** Business logic lives in TypeScript. Rust is limited to what needs native Windows APIs or the Tauri shell.

## Process model

```text
┌──────────────────────────── BTCortex.exe (Tauri 2, Rust) ────────────────────────────┐
│  WebView2 ── React interface                                                          │
│     │  invoke('orchestrator_call', {method, params})   ▲ events: orchestrator-event   │
│     ▼                                                   │         orchestrator-status  │
│  Native shell: window, tray, start-up, single instance, logs, DPAPI, sidecar          │
│     │  stdin/stdout: newline-delimited JSON-RPC 2.0 (both directions)                  │
└─────┼─────────────────────────────────────────────────────────────────────────────────┘
      ▼
 btcortex-orchestrator.exe (Node.js single executable, TypeScript)
      │  service adapters, monitoring, persistence (SQLite), jobs, logging
      ├── bitcoind.exe (detached, per node profile) ── JSON-RPC over loopback, cookie authentication
      ├── Sparrow.exe (opened on request, detached, not supervised) ── reads the node's cookie itself
      └── further services as integrations land (Tor, Fulcrum, …)
```

- **WebView (React).** Presentation and interaction only. It has no shell, file-system or process permissions; its single privileged entry point is the `orchestrator_call` command.
- **Native shell (Rust).** Starts the orchestrator as a Tauri sidecar, relays requests and events, restarts the orchestrator with back-off after a crash (at most three quick restarts), owns Windows DPAPI, the notification-area icon and starting with Windows (`src-tauri/src/shell.rs`), and stops the orchestrator gracefully when the application exits.
- **Orchestrator (TypeScript on Node.js).** All application logic: node profiles, verified installations, Bitcoin Core lifecycle, connected applications such as Sparrow, monitoring, background jobs, persistence and structured logging.
- **Managed services.** Started detached, so closing BTCortex never kills them abruptly; each managed node's profile decides whether it starts when BTCortex starts (`startWithBtcortex`, on for nodes BTCortex sets up) and whether it keeps running after BTCortex quits (`keepRunningOnExit`, off for them). A node's Electrum server follows it, and tor keeps running while a node that keeps running uses it. Services are always stopped through their own graceful mechanism (for Bitcoin Core: RPC `stop`).

## Communication boundary

The wire protocol between shell and orchestrator is JSON-RPC 2.0, one JSON document per line, in both directions (`packages/contracts/src/jsonrpc.ts`).

- **Origin stamping.** The shell adds `origin: "ui"` to every request it forwards from the WebView, and `origin: "shell"` to its own. The WebView cannot forge the origin because it never writes to the channel. Requests without an origin are treated as `ui`.
- **Method registry.** Every orchestrator method is declared once in `packages/contracts/src/methods.ts` with its parameter schema, result schema, allowed origins and risk class (`read`, `write`, `dangerous`). The orchestrator validates parameters before a handler runs and validates the result before it leaves, so contract drift fails loudly. The interface derives its typed client from the same declarations and validates responses again.
- **Shell methods.** The orchestrator can call the shell only for `vault.protect` and `vault.unprotect` (`shellMethods`). The shell accepts those only on the sidecar channel.
- **Events.** The orchestrator publishes `event` notifications (`orchestrator.ready`, `node.status`, `nodes.changed`, `job.updated`), which the shell relays to the WebView unchanged; the interface writes them straight into its query cache instead of polling.
- **Errors.** Application failures travel as JSON-RPC errors whose `data` is an `AppError`: what happened, the affected component, whether user data is at risk, the likely cause, redacted details and recovery actions (specification section 30). Unexpected internal errors are reported generically; their details stay in the orchestrator log.

Existing installations (for example `%APPDATA%\Bitcoin`) are detected read-only and never modified, moved or deleted.

Sparrow keeps its own settings in `%APPDATA%\Sparrow`. BTCortex changes only the connection keys in the settings file of the node's network, and only while Sparrow is closed; it backs the file up next to itself first. Sparrow's wallets are never read or modified.

## Persistence

SQLite through Node's built-in `node:sqlite` (no native add-ons), in WAL mode. Migrations are append-only and recorded in `schema_migrations`; each runs in a transaction and rolls back completely on failure. A database written by a newer BTCortex is refused rather than downgraded (specification section 28). Profiles are validated with their Zod schema when read, so a corrupted row cannot inject malformed data.

## Credential protection

Remote RPC passwords and similar secrets are encrypted with Windows DPAPI (current-user scope, BTCortex-specific entropy) by the native shell and stored only as protected blobs. The orchestrator decrypts a secret into memory only when it needs it. Local Bitcoin Core nodes use cookie authentication, so no secret is stored for them at all. The WebView never receives secrets; preferences in WebView storage are limited to the theme and sidebar state.

## Bitcoin Core integration

- **Verified installation** (`packages/integrations/bitcoin-core/src/release`, through the shared pipeline in `packages/installation-manager`): resolves the latest final release, downloads `SHA256SUMS` and `SHA256SUMS.asc`, verifies the OpenPGP signatures against 40 builder keys pinned from `bitcoin-core/guix.sigs` at a recorded commit, requires at least three distinct trusted signers (counted per builder, so one builder's two keys count once), downloads the signed ZIP with resumable, streaming SHA-256 verification, extracts it with path-traversal, symbolic-link and size checks, verifies the Authenticode signature of every executable, and records the full verification report next to the runtime. No administrator rights, no PATH changes, no URI handlers.
- **Bitcoin Knots** (`packages/integrations/bitcoin-knots`; `SetupService` with `implementation: 'bitcoin-knots'`): set up only on request and only with `acceptDifferentChain: true`, checked when the job starts and again against the release it resolves (29.4.1 and later follow a chain Bitcoin Core rejects). The pgpverifiable ZIP from bitcoinknots.org is verified through the same pipeline against 20 builder keys pinned from `bitcoinknots/guix.sigs` (some are published as binary keys and bundled armoured), with a threshold of three builders and Luke Dashjr's signature required (`requiredSigners`); Authenticode is recorded only, since the builds are unsigned, and an acceptance check runs `bitcoind -version`, which must report Knots of that version. Runtimes go to `installations\bitcoin-knots`, the node manager starts a Knots profile only from there, its `bitcoin.conf` is marked as Knots data, its usage cannot be an Electrum back end, and `nodes.useRuntime` refuses to move a node between Knots and Bitcoin Core. `tests/integration/bitcoin-knots.test.ts` sets up and starts a real Knots 29.4.2 regtest node this way.
- **Configuration** (`packages/bitcoin-config`): generated from hardware-aware recommendations (pruning when the full chain does not fit, memory-aware `dbcache`, `listen=0` so there is no router mapping or firewall prompt), pins `chain=` so the directory can never start on mainnet by accident, validated before it is written, and written with `wx` so an existing file is never overwritten.
- **Configuration editing** (`apps/orchestrator/src/nodes/config-service.ts`, `apps/desktop/src/features/config`): a graphical editor by category and a raw editor work on one shared draft, checked as the user types with the same validator the orchestrator uses.
  - _Reading as Bitcoin Core reads._ The parser mirrors `GetConfigOptions` and `InterpretKey`: only space, tab, CR and LF are trimmed, section names are taken verbatim, a leading dot means the global scope, a prefixed name inside a section is an ignored unknown option (reported as an error), `nofoo=0` is a double negative, global negations apply to network-only options on every network, and the chain selectors count only in the global scope. Any difference would let an edit look harmless while Bitcoin Core reads it otherwise.
  - _Secrets._ Passwords and `rpcauth` hashes are replaced by numbered placeholders before the file leaves the orchestrator, from the value to the end of the line, and so are credentials on malformed lines, in comments (whatever their spelling) and in trailing comments. Saving puts a value back only where masking itself would have put it, for the same option, and only if masking the restored line hides exactly that value again, so an edit can never move a secret into a comment, an option name or another option, nor glue it to an option name where the next reading would show it. Messages about lines holding a secret never quote them, and Bitcoin Core's own parse errors are redacted everywhere. Revisions are keyed with a per-process secret, so they cannot be used to test password guesses.
  - _Saving._ Every check is repeated; changes to the settings BTCortex relies on (network selection, RPC port, cookie, credentials, data directory, `includeconf`, `settings`) are refused, and an `includeconf` that was not there before is refused whatever negations surround it, because Bitcoin Core reads the global and the network includes separately; options that widen exposure, run commands or rebuild data need explicit confirmation, including returning `listen` or `natpmp` to their default, which is on. A file that changed since it was read, or that is not UTF-8, is not overwritten. Saves run one at a time per node; the previous file is kept as a backup (the ten newest are kept) and the new one is written to a unique temporary file, flushed to disk and renamed into place.
  - _Editing._ One option is changed with `setOption` from `packages/bitcoin-config`, shared with the orchestrator: a value goes where Bitcoin Core reads it for the network, and list options are edited in place, so lines whose value stays keep their comments and positions. A draft stays on the revision it was started from: if the file changes on disk meanwhile, the page says so and the save is refused rather than undoing the other change. Hidden values are never put into a field; typing replaces them, and a placeholder that was edited into is refused before saving. When the orchestrator refuses a save, its reasons are listed in the review.
  - _Earlier versions._ The backups are the file's history (`nodes.config.history`, newest first, the time each was replaced taken from its name). `nodes.config.version` shows one with secrets hidden and what restoring it would change against the file as it is now, as effective values per option, with secret options marked but never given a value. `nodes.config.restore` reads the kept bytes and puts them back through the whole save (revision check, validation, settings BTCortex relies on, confirmation of risky options), so the current file becomes a version in turn. Only names BTCortex gives (`bitcoin.conf.btcortex-<time>-<random>.bak`) are accepted, so a version id can never name another file.
  - _Export._ `nodes.config.export` writes the file with every secret hidden and a header saying so to a `.conf` or `.txt` path chosen in the system's Save dialog, never under the name `bitcoin.conf`. Importing is done by pasting settings into the file tab: BTCortex does not read files that may hold secrets into the window.
  - _Restart._ Whether the running node still uses older settings is known exactly when BTCortex started it, and otherwise judged from the file's modification time. Nodes BTCortex did not set up are shown read-only, without a restart button.
- **Lifecycle** (`src/node/process.ts`): `bitcoind.exe` is spawned directly (no shell), detached, with `-datadir`, `-chain`, `-server=1` and `-printtoconsole=0`; console output goes to a file so early start-up errors are kept. Stopping always uses RPC `stop`; a restart stops the node and starts it again once it has shut down. `nodes.lifecycle.configure` sets the start and quit policies (migration 4 added `start_with_btcortex`); once every service has initialised, the orchestrator starts the managed nodes chosen to start with it, unless their bitcoind still runs.
- **Monitoring** (`apps/orchestrator/src/nodes/node-manager.ts`): one polling loop per node with an interval that adapts to its state (2 s starting, 5 s synchronising, 15 s synchronised), exponential back-off up to 60 s when unreachable, no overlapping requests, a check that the node's chain matches its profile, and a synchronisation estimate that is always labelled as an estimate.

## Network and peers

`apps/orchestrator/src/nodes/peer-service.ts` lists peers, the reachable networks and their proxies, manually added peers and bans, and acts on them through RPC (`disconnectnode`, `addnode`, `setban`, `clearbanned`). Bans take the address without its port; loopback addresses and `/0` subnets are refused, because incoming Tor and I2P peers all arrive from the computer's own address and a ban on it would cut the node off from those networks. Bitcoin Core's refusals (already added, already banned, not found) become plain explanations. Connections and disconnections are recorded by comparing the peer list about once a minute, in memory only. Peer addresses are shown and never sent anywhere; no location is guessed from them.

## Mempool

`apps/orchestrator/src/nodes/mempool-service.ts` describes the node's own mempool and says so wherever it is shown, because other nodes can hold other transactions.

- **Distribution without downloading the mempool**: the fee-rate buckets and the lowest fee rate that would make the next block come from the cluster mempool's cumulative fee-rate diagram (`getmempoolfeeratediagram`, Bitcoin Core 31.0 and later), which lists the mempool in mining order. Older nodes and other implementations show no distribution rather than an approximation.
- **Estimates and policy**: `estimatesmartfee` (economical) for targets from the next block to a week; `getmempoolinfo` for the minimum relay and incremental fee rates, the current minimum to enter, full replace-by-fee, the cluster limits and the OP_RETURN data limit. Relay features that came with a release rather than a setting (package relay, TRUC, Pay-to-Anchor, ephemeral dust, cluster mempool) are read from the version in `getnetworkinfo`, for Bitcoin Core only: Bitcoin Knots reports similar versions with a different policy, so for it BTCortex says it cannot tell.
- **One transaction**: `getmempoolentry` gives the fee rate of the chunk the transaction will be mined with, which is the rate that really counts when a child pays for its parent; `getmempoolcluster` gives the chunks of its whole cluster in mining order, and `getrawtransaction` its outputs. A transaction that is not in the mempool is reported as such, not as a failure of the node.
- **Replacement terms**: the least a same-size replacement must pay is the fees of the transaction and its descendants plus the incremental relay fee for its own size, rounded up as Bitcoin Core rounds it. The integration test builds replacements against real bitcoind 31.1 and checks that one satoshi less is refused with "insufficient fee" and the stated minimum is accepted. Under the cluster mempool a replacement must also improve the fee-rate diagram, which is stated rather than predicted.
- **Trend** (`metrics-history.ts`): every successful status poll is reduced to one sample a minute (height, peers, mempool size, transaction count and minimum fee), kept in memory for 24 hours. The interface shows one measure at a time, each on its own scale.
- **Charts** (`apps/desktop/src/components/charts`): hand-drawn SVG at one unit per pixel, so labels keep their size; one series in the validated `--chart-1` colour with no legend, tooltips beside the mark with the value first, keyboard access to every column and sample, and a table view of the same numbers.

## Block explorer

BTCortex's own explorer (`apps/orchestrator/src/explorer/explorer-service.ts`, `explorer.*` methods; specification section 12) reads from the chosen node, so nobody outside learns what is looked up, with one exception the user sets up: address lookups go to an Electrum server, the node's own or, while that one is not ready, one on another computer added for the node, which then learns the addresses.

- **Search** works out what was entered: a height or block hash (`getblockhash`, `getblockheader`), a transaction id (`getrawtransaction`), an address for the node's network (`validateaddress`), a raw transaction (`decoderawtransaction`) or a script (`decodescript`).
- **Blocks** come from `getblock` (verbosity 2) and `getblockstats`, kept for the blocks looked at last since they never change; a pruned block shows its header only, and says so. Transactions are listed a page at a time with their fee rates.
- **Transactions** come from `getrawtransaction` (verbosity 2). For confirmed transactions it names the coins each input spends while the block's undo data is kept; for unconfirmed ones the fee comes from `getmempoolentry` and the coins from the unspent set (`gettxout` without the mempool, so no index is needed) or from an unconfirmed parent. Outputs say whether they are still unspent (`gettxout` with the mempool). Unconfirmed transactions show their ancestors and descendants and are followed until they have a few confirmations. Without the transaction index, confirmed transactions cannot be found by id, which the explorer says.
- **Raw transactions** are decoded and checked with `testmempoolaccept`, which never broadcasts them.
- **Addresses**: Bitcoin Core keeps no index of addresses, so balances, history and unspent coins come from an Electrum server (`blockchain.scripthash.*`, the script hash being the reversed SHA-256 of the script): the node's own, or, while that one is not ready, one on another computer added for the node, and the address view names the server that answered; without either, the explorer shows the script and says why there is no history.
- **Overview**: tip, difficulty, hash rate (`getnetworkhashps` over 120 blocks), transaction count and rate (`getchaintxstats`), Bitcoin Core's fee estimates, the mempool and the latest blocks with their median fee rates.
- **Explorers on other computers** (`apps/orchestrator/src/explorer/remote-explorer-service.ts`, `packages/integrations/esplora`; `explorers.remote.*`): a mempool or Esplora instance, reached directly or through BTCortex's tor (one SOCKS stream per explorer). Its Esplora API is looked for under `/api` and, for Esplora, at the root; the test and every check ask only `blocks/tip/height`, `block-height/0`, whose hash tells the chain, and, for an explorer added for a node, `block-height/<h>` two blocks below the lower of the two tips, whose hash must match the node's; answers are plain text of bounded size. One added for a node must follow that node's chain (its genesis compared with the node's `getblockhash 0`), and its status says how many blocks it is behind. The monitoring raises an alert when one has not answered for five minutes, and at once when it follows another chain. `explorers.remote.open` builds the page address (`/tx/<txid>`, `/block/<hash>`, `/address/<address>`) from the stored address and validated items, and the orchestrator opens it with Windows' URL handler (`rundll32 url.dll,FileProtocolHandler`, no shell), so the WebView's own permission stays HTTPS-only while local `http://` explorers still open; an onion explorer's address is returned for Tor Browser instead. They appear under Remote infrastructure, with a connection test, and as mempool and Esplora adapters at the connected level in the catalogue.
- **Tests**: `tests/integration/explorer.test.ts` runs every view against a real regtest bitcoind with and without the transaction index, and the address lookups against a real Fulcrum.

## Storage and indexing

`apps/orchestrator/src/nodes/storage-service.ts` (`nodes.storage`) combines what Bitcoin Core reports with what can be measured on this computer.

- **From Bitcoin Core**: `getblockchaininfo` for the size of block and undo files and the pruning mode, target and height (the date of the oldest block kept comes from its header); `getindexinfo` for the indexes that are switched on and how far each has been built.
- **Measured locally**, for nodes whose files are on this computer: the size of each folder of the network (blocks, chainstate, each index, wallets, other files), the wallets (folders holding a `wallet.dat`), BTCortex's own data without the managed nodes' data directories, and Sparrow's folder. Links and junctions are not followed. Measurements are reused for a minute, so the page can refresh without walking the block folders each time.
- **The disk** (`apps/orchestrator/src/platform/disks.ts`): free and total space from `statfs`, and whether the volume is an SSD or a hard disk and how it is connected, from Windows' Storage module (`Get-Partition`, `Get-PhysicalDisk`), which needs no administrator rights; asked once per volume.
- **Warnings** (`storageWarnings`): less than 2 GiB free (Bitcoin Core stops below 50 MiB), less than 10 GiB free, an unpruned chain still downloading that will not fit, a hard disk, an external drive, and index folders left behind by an index that is switched off.
- **Consequences**: the interface explains what switching to pruning or back to a full node would mean, and that the transaction and spent-output indexes are impossible on a pruned node, using the chain size estimates in `packages/bitcoin-config`.
- **Changes** (`nodes.storage.configure`, nodes BTCortex set up only, always confirmed): indexes switched on or off and pruning switched on, retargeted or off. The change is made with `setOption` from `packages/bitcoin-config` (shared with the configuration editor) on the masked file and saved through the configuration service, so it gets the same checks, backup and atomic write. Combinations Bitcoin Core refuses are refused first with an explanation (pruning with the transaction or spent-output index; serving filters without the block filter index). The node is then restarted. Leaving pruning restarts it with `-reindex`, after checking that the whole chain fits on the disk.
- **Maintenance**: `verifychain` at Bitcoin Core's default depth (read-only, for every node); `-reindex-chainstate` (not on a pruned node) and `-reindex` as one-shot start arguments that never reach `bitcoin.conf` (`NodeManager.restart` accepts only these two); deleting the folder of an index that is off both in the running node and in `bitcoin.conf`.
- **Verified** against real bitcoind 31.1 on regtest (`tests/integration/storage-actions.test.ts`): indexes switched on and built after the restart, the chain verified, the chainstate rebuilt with the flag absent from the file, the transaction index refused with pruning, pruning switched on and then off again through a full reindex with the chain intact.

## Storage across BTCortex

`apps/orchestrator/src/storage/` (`storage.overview`, `storage.clean`; specification section 27) gives the app-wide view; the per-node detail stays in `nodes.storage` above.

- **Folders** (`DiskUsageService`): the database (with its WAL and shared-memory files), installations, logs, downloads, temporary files, exports, tor's folder and the Lightning channel backups, each node's data directory (read-only for nodes BTCortex did not set up), the wallets of the Electrum copy BTCortex installed (when that folder exists), each Electrum server's index (the size the Electrum service measured last) and the backup destination, each with its owner, the page that manages it and its size. Sizes come from `folderSize` (links and junctions not followed) and volumes from `measureVolume`, both in `platform/disks.ts`; each volume is measured once with the folders on it. A measurement is reused for ten minutes, but whether a job is running is worked out on every request.
- **Clean-ups**: only files directly inside `…\downloads` (unfinished downloads and archives of installations that failed; finished archives are deleted after extraction) and `…\tmp` (copies made while a wallet is backed up or restored), and only those last changed more than an hour ago. Both are refused (`storage.busy`) while any job is queued or running, and the interface asks first. Nothing else is ever deleted from here, whatever its name.
- **Virtual disks** (`virtual-disks.ts`): WSL 2 distributions are read from `HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss` (`BasePath`, `VhdFileName`, version 2 only) through PowerShell without administrator rights; Docker Desktop's data disk is looked for next to its `docker-desktop` distribution and in `%LOCALAPPDATA%\Docker\wsl\disk`, since Docker Desktop 4.30 keeps it outside a distribution of its own. Only files that exist are listed, read-only: BTCortex uses neither WSL2 nor Docker.
- **Forecasts**: the monitoring samples each node's `size_on_disk` once a minute (`node.size`); a least-squares line through up to 30 days of hourly averages gives the growth per day, and the free space divided by it the days left. Less than a day of samples, or growth below 1 MiB a day, gives no forecast.
- **Interface** (`apps/desktop/src/features/disk-usage/`): volumes with a capacity meter whose value is also given in words, a forecast per node (a warning that says what to do when the disk would be full within 30 days), the folders by size with their owners, and the clean-ups. A job being queued or ending invalidates the view, so the clean-up buttons follow it.
- **Tests**: `apps/orchestrator/src/storage/disk-usage.test.ts` (owners, leftovers older than an hour only, refusal while a job runs, forecasts, virtual disks and where they are looked for) and `apps/desktop/src/features/disk-usage/disk-usage.test.tsx`.

## Service orchestration and integration modules

Specification sections 24.1 (Service Orchestration) and 29. `apps/orchestrator/src/services/service-module.ts` is the contract every integration module fulfils, around the catalogue's `ServiceAdapter`:

- **Facets**: metadata (id, name, evidence status, support level), dependencies on other integrations, capability detection (the adapter's capabilities and `state()`), installation (`install()` as a job, `uninstall(version)`), lifecycle (`run(instance, start | stop | restart)` among the actions each instance offers), configuration (where and how), health (per instance), metrics (series of the monitoring history), logs (sources of the log centre), updates (the update centre's product), documentation (a help document and section) and the interface (routes). A facet an integration does not have is left out and never offered.
- **Trust**: modules are built into BTCortex and reviewed with it; nothing is loaded at run time. Each receives only the services it needs through its options and declares what it may do — run programs, write its own files, use the network, run Tor, talk to nodes, use stored credentials — which the interface shows. The declaration informs; it is not a sandbox, since modules run inside the orchestrator.
- **Modules** (`services/modules.ts`): Bitcoin Core and Bitcoin Knots nodes (lifecycle only for nodes BTCortex set up; a node needs tor when it routes all traffic through Tor, keeps to Tor or publishes an onion service, and uses it when it only adds onion peers), Fulcrum (one server per node, needing its node, and using tor for its onion service) and tor.
- **Orchestration** (`orchestration/orchestration-service.ts`, `services.overview`, `services.plan`, `services.run`): instances listed in the order they start; a plan starts what something needs first (as the services themselves would: a node starts tor itself when its routing needs it) and stops what needs something first, says what else is affected without being changed, and is refused with a reason when a hard requirement cannot be met. `all` plans everything at once, in dependency order. A plan runs only with `confirmed: true`, step by step, one plan at a time, stopping at the first step that fails and saying which were done.
- **Sample** (`services/sample/example-module.ts`): a module for a stand-in program kept in memory, with every facet, which its test drives through the orchestration — detection, installation as a job, configuration, start with its node first, health, logs and metrics, an update, stopping when its node stops, and removal of the old version.
- **Interface** (`apps/desktop/src/features/orchestration/`): the services with their state, what each needs and what needs it, their logs, and actions that show the plan first; the modules with their evidence, permissions, dependencies, help and updates.
- **Tests**: `apps/orchestrator/src/orchestration/orchestration.test.ts` (order, plans, consequences, refusals, runs and failures, the sample's lifecycle), `apps/orchestrator/src/services/modules.test.ts` and `apps/desktop/src/features/orchestration/orchestration.test.tsx`.

## Installed software

`apps/orchestrator/src/installations/installation-service.ts` manages what BTCortex installed from verified releases (specification section 17.3).

- **Records**: the installer (`packages/installation-manager`) now records the SHA-256 and size of every extracted file next to the signature and Authenticode results, so an installation can be checked again later (`checkInstalledFiles`). Versions installed before this have no file hashes and are reported as not checkable; installing them again records them. The whole pipeline (signed manifest, checksum, download, extraction, required files, record, activation) is unit-tested against an in-memory release server.
- **Updates**: the newest final release is asked from the same official sources as the first installation, at most every ten minutes. An update is a background job that installs the new version into its own folder, so it never touches the version a node runs; nodes are moved explicitly (`nodes.useRuntime`), forward only, because Bitcoin Core does not promise that an older version reads an upgraded data directory, never between Bitcoin Core and Bitcoin Knots, and are restarted if running. Bitcoin Knots is listed and checked for updates only once it is installed.
- **Removal**: a version is deleted only when no node uses it and, for Sparrow, when Sparrow is not open.

## Catalogue and service adapters

The Bitcoin Ecosystem Catalogue (specification section 6) is built from the research records, and what BTCortex can do with an entry is declared separately, so a target support level is never presented as a working integration.

- **Data** (`packages/catalogue`): `scripts/research/build-catalogue.mjs` turns the catalogue-eligible research records into `catalogue.generated.json`, deterministically; a test fails when the file is out of date, and the records are checked against the shared schema as they load. The orchestrator executable bundles the data, and its smoke test reads it back.
- **Service adapters** (`apps/orchestrator/src/services`): every integration declares its evidence level (the same levels as `docs/implementation/features.json`, kept in step by a test), the support level it delivers today, the operations it supports and where it is managed, and reports its live state. Operations run through the feature that owns them; an operation an adapter does not declare is not offered. Today 22 adapters are registered (`apps/orchestrator/src/main.ts`): Bitcoin Core, Bitcoin Knots, Fulcrum, Tor and HWI as fully managed; Sparrow, Electrum, LND, BTCPay Server, mempool and Esplora explorers, and the signing devices (Trezor, Ledger, BitBox02, COLDCARD, Jade and KeepKey through HWI; Passport, Keystone and Krux by QR codes or PSBT files on microSD, SeedSigner by QR codes only) as connected applications; Trezor Suite as an external launcher. Every other catalogue entry is research only. One adapter failing does not hide the rest of the catalogue.
- **Dependency resolver** (`resolveDependencies`, specification section 17.2): for an entry, which requirements are met by what is on this computer, which conflicting entries are present, and the order to set up the required chain, preferring alternatives that are already present. Devices and hosted services are treated as something the user brings, not as installation steps, so a signing device and its companion app requiring each other is not reported as a loop; real loops are detected. A test runs it over every researched entry.
- **Interface** (`apps/desktop/src/features/catalogue`): search and filters (category, target level, available now, native on Windows), entries grouped by category with their target level and Windows support, and a page per entry with what BTCortex does today, verified project information, compatibility, dependencies checked against this computer, security notes and sources. Outside links open in the user's browser through the shell's opener (https only); the WebView never leaves BTCortex.

## RPC console

`apps/orchestrator/src/nodes/rpc-console-service.ts` lists the node's methods from its own `help`, classified with the risk table in `packages/bitcoin-rpc/src/catalogue.ts` (read, slow, changes state, dangerous; methods whose parameters or results can hold secrets are marked). The orchestrator enforces the rules rather than trusting the interface: dangerous methods need confirmation, unknown methods count as dangerous and secret, and methods that would pass private keys or wallet passphrases through BTCortex, test-only methods and `stop` are refused. Read-only mode is an interface setting, on by default.

## Sparrow integration

Sparrow is connected to a node with one action on the node's page (`apps.sparrow.connect`, a background job; `apps/orchestrator/src/apps/sparrow-service.ts`).

- **Installation** (`packages/integrations/sparrow/src/release.ts`): the portable ZIP, which brings its own Java runtime and needs no installer, registry entries or URI handlers. The release manifest must carry a valid signature from Craig Raw's key, pinned by fingerprint and refreshed with `scripts/update-signing-key.mjs`; the archive must match the signed checksum and is extracted with the same safety checks as Bitcoin Core. The Authenticode result is recorded, not required, because whether Sparrow's executables are code-signed is not established.
- **Connection** (`src/config.ts`): cookie authentication only, because Sparrow would store an RPC password in plain text. For nodes BTCortex manages, the RPC address and data directory come from the node profile; for an existing local node the root data directory is derived from its cookie path. Sparrow reads the cookie itself, so it keeps working after the node restarts.
- **Checks before anything changes**: Sparrow must be closed, because it rewrites its whole settings file when it exits. A server the user configured is replaced only with explicit consent. So is a fixed start-up network ("Restart in …" marker files override Sparrow's network flag); those files are set aside as backups rather than deleted. Every other setting is preserved, the original file is backed up, and the new one is written to a temporary file and renamed into place.
- **Launch**: `Sparrow.exe -n <network>`, detached. Sparrow then creates its own watch-only wallet (`cormorant`) in Bitcoin Core; BTCortex leaves it alone.
- **Status** (`apps.sparrow.status`): whether Sparrow is installed, open and set to this node, and anything that would need consent.

## Tor

BTCortex runs its own tor for the nodes (specification section 10; the full reasoning is in [`PRIVACY_AND_TOR.md`](PRIVACY_AND_TOR.md)).

- **Installation** (`packages/integrations/tor/src/release.ts`): the Tor Expert Bundle, the Tor Project's standalone tor for Windows. The current version is read from Tor Browser's `download-windows-x86_64.json`; the bundle comes from dist.torproject.org, or the archive mirror for versions no longer there. Both `sha256sums-signed-build.txt` and the archive itself must carry a valid signature from the Tor Browser Developers key, pinned by its primary fingerprint (`scripts/update-signing-key.mjs`) and refreshed from the Tor Project's Web Key Directory before each installation, because its signing subkeys rotate. The installer gained a tar.gz extractor with the ZIP extractor's rules (regular files and folders only, every path checked, a size limit applied while decompressing) and an acceptance check: the extracted `tor.exe --version` must run before the installation is activated. tor.exe is not code-signed, so Authenticode is recorded only.
- **Process** (`src/torrc.ts`, `src/process.ts`; `apps/orchestrator/src/tor/tor-service.ts`): one tor per user, without administrator rights or a Windows service. The torrc holds only path-free options (SOCKS ports for nodes and for applications, a control port, all on 127.0.0.1, cookie authentication, notice-level logs); every path is its own command-line argument. The control port is not tor's usual 9051, because Bitcoin Core looks there by default and, when it accepts incoming connections, would publish an onion service without anyone asking. Ports are chosen at the first start (the usual ones when free) and kept, so node settings pointing at them stay valid. tor runs detached and writes its output to a file, like bitcoind; a node that keeps running after BTCortex closes keeps its tor, and the next session finds tor through its control port and cookie instead of starting another one. After a crash tor is restarted after 5, 15 and 45 seconds, then left stopped with the reason shown.
- **Control** (`src/control.ts`): the control protocol with SAFECOOKIE only, so the cookie never crosses the socket and a program impersonating tor on the port is detected; the cookie file tor reports must be BTCortex's own. Bootstrap progress, problems, circuits, network liveness, clock skew and version warnings come from tor's events and are published to the interface as `tor.status` events.
- **Other tor** (`src/detect.ts`): the usual ports of a separate tor, Tor Browser and Wasabi are probed with `PROTOCOLINFO` only; their cookies are never read and nothing is sent through their SOCKS ports.
- **Nodes** (`apps/orchestrator/src/nodes/privacy.ts`, `privacy-service.ts`): a managed node connects directly, adds onion peers, sends every connection through Tor, or uses Tor only; it can have an onion service bound to loopback only, and send its transactions with `privatebroadcast` (Bitcoin Core 31.1 and later). Each mode is a fixed set of `bitcoin.conf` options, written through the configuration service (backup, checks) and applied with a restart; anything else is shown as set up by hand. `onion=` is always written in Tor modes, because without it Bitcoin Core falls back to 127.0.0.1:9050, possibly another program's tor, when tor reports no SOCKS port. The node manager starts tor before a node that routes through it, and does not start a node that would have no connections without tor.
- **I2P** (`packages/integrations/i2p`, `apps/orchestrator/src/i2p/i2p-router.ts`; method `i2p.status`): BTCortex does not install or run an I2P router; it finds the user's. The SAM bridge on `127.0.0.1:7656` is greeted with `HELLO VERSION MIN=3.1 MAX=3.3` (a `NOVERSION` reply, another program or silence each get their own explanation), and the listening program is named from `Get-NetTCPConnection`. When nothing answers there, i2pd's console on 7070 and the Java router's on 7657 are asked for their pages, to tell a router whose bridge is off from no router; the answer is kept for 30 seconds. A node's I2P option, alongside any Tor mode, is `i2psam=127.0.0.1:7656` with `i2pacceptincoming=0` (a transient I2P address per connection), plus `onlynet=i2p` in Tor-only mode; I2P set up any other way makes the routing "set up by hand". `nodes.privacy.configure` refuses to turn I2P on while no router answers (`privacy.i2p-router-missing`); a node using I2P starts without its router, with a warning in the log. `tests/integration/privacy.test.ts` runs a stand-in SAM bridge that records Bitcoin Core's greeting and refuses the session.

## Hardware wallets

Signing devices reach the user's own node through Bitcoin Core's external signer support, with BTCortex's verified HWI as the signer (specification section 9; the full description is in [`WALLET_INTEGRATIONS.md`](WALLET_INTEGRATIONS.md)).

- **Recognition** (`packages/integrations/hardware-wallets`): Windows' device list read through WMI, matched against the USB identities HWI 3.2.0 uses; composite devices are grouped, Windows' problem codes reported, and generic serial adapters counted only as serial ports and only as "possibly a Jade". Nothing is opened.
- **HWI** (`packages/integrations/hwi`): installed through the shared installer, which gained clear-signed manifests (only the signed text is trusted) and checks of the files inside an archive when the manifest lists them. The client runs hwi.exe without a window, passes PSBTs on standard input as Bitcoin Core does, validates every argument, and exposes no device set-up, wiping, restore, backup, PIN or passphrase commands. HWI's results include device labels and are never logged.
- **Node** (`apps/orchestrator/src/nodes/signer-service.ts`): sets `signer=` to the quoted path of the newest verified HWI on nodes BTCortex manages (written through the configuration service, so a backup is kept) and restarts them; lists the devices Bitcoin Core finds; creates watch-only wallets with `external_signer`; shows only wallets bound to a device. Receiving addresses are shown on the device with `walletdisplayaddress`, which Bitcoin Core refuses when the device echoes another address. Transactions are built with `walletcreatefundedpsbt`, reviewed from `decodepsbt`, `analyzepsbt` and `getaddressinfo` (change is marked), signed with `walletprocesspsbt` only on request, and broadcast with `sendrawtransaction` only on request; signing and broadcasting are `dangerous` methods that need `confirmed: true`. PSBT files are read and written by the orchestrator at paths the user chose in the system's dialogs.
- **Trezor Suite** (`trezor-suite.ts`, `packages/installation-manager/src/signed-installer.ts`): a vendor installer without a checksum file is trusted only when its detached OpenPGP signature verifies against the pinned SatoshiLabs key and its Authenticode signature names the expected publisher; it is then run silently for the current user (`/S /currentuser`), the installed program must exist, and the installer is deleted. The deprecated standalone Trezor Bridge is detected by its folder, process and port.
- **QR codes** (`packages/integrations/hardware-wallets/src/qr.ts`): PSBTs as `ur:crypto-psbt` Uniform Resources (the PSBT as a CBOR byte string), fountain-coded into twice as many parts as fragments when they do not fit one code, in upper case for the QR alphanumeric mode; QR matrices are made in the orchestrator and drawn by the interface as SVG paths. Reading is stateless: the interface sends every distinct code its camera (jsQR) has read and gets the progress back. A round-trip test renders the matrices to pixels and reads them with jsQR.
- **Tests**: `tests/integration/hardware-signer.test.ts` runs the whole path with a real bitcoind and a simulated device (`tests/integration/support/mock-signer.mjs`, which answers like HWI and signs with a regtest wallet holding the keys), from a BTCortex folder whose path contains a space.

## Electrum servers

Fulcrum, the only Electrum server with native Windows releases, runs next to nodes on this computer so that Electrum wallets can use them (specification section 7; research in [`research/notes/electrum-indexers-explorers.md`](research/notes/electrum-indexers-explorers.md) §3).

- **Installation** (`packages/integrations/fulcrum/src/release.ts`): the portable ZIP through the shared installer. `Fulcrum-<version>-shasums.txt` must carry a valid signature from Calin Culianu's pinned key, which is DSA-2048: OpenPGP.js rejects DSA by default, so the installer accepts it for that one pinned key only and only at 2048 bits or more (`TrustedKey.allowDsa`). `FulcrumAdmin.exe`, a packed Python script that antivirus programs have flagged and BTCortex does not need, is left out (`skippedFiles`). `Fulcrum.exe` is not code-signed upstream, so Authenticode is recorded only; it must report its version before the installation is activated.
- **Configuration** (`config.ts`): written before every start. The Electrum, admin and statistics ports are bound to `127.0.0.1` (Fulcrum's own default for the Electrum port is `0.0.0.0`); peer discovery, announcements and UPnP are off; the node's cookie file is named, and RPC passwords travel only in the `RPCUSER` and `RPCPASSWORD` variables, which Fulcrum hides in its statistics. RocksDB, which holds the index, cannot open folders whose path has characters outside ASCII (tested with 2.1.4), so such folders are given to Fulcrum by their 8.3 short name.
- **Set-up** (`apps/orchestrator/src/electrum/`): a plan first (eligibility, index folder, room needed from the node's block files or the network's expected size while it synchronises, node settings, restart), then a job: Fulcrum installed, the folder created with a marker file naming its node, ports chosen and kept, and on nodes BTCortex manages `txindex=1` (and `zmqpubhashblock` on loopback when the node restarts anyway) written through the configuration service, which keeps a backup. A node created as an Electrum back end gets `txindex=1` from the start and its Electrum server set up afterwards.
- **Running**: one reconcile loop starts Fulcrum when its node runs, has caught up and has built its transaction index, and follows it through `/stats` (open from start-up: indexed height against the node's) and the admin port (open once caught up: wallets connected, memory). Every minute an Electrum probe (`server.version`, `server.features`, `blockchain.headers.subscribe`) checks the port wallets use and compares the genesis hash with the node's; a server on another chain is stopped. Fulcrum runs detached with its output in `logs\fulcrum-<node>.log`, keeps serving a node that keeps running after BTCortex closes, and is found again through its recorded process (checked to be `Fulcrum.exe`). After an unexpected exit it is started again after 5, 15 and 45 seconds, then left stopped.
- **Stopping**: before its node stops (`NodeManager.beforeStop`), and before BTCortex stops the nodes when it closes, through the admin port's `stop` once the index has caught up. During the initial indexing there is no admin port and no console to send Ctrl+C to, so Fulcrum is ended, which Fulcrum 2 is designed to survive (at most a few blocks are indexed again).
- **Access from other devices**: on request, the server is published as an onion service by BTCortex's tor through its control port (`ADD_ONION` with `Flags=Detach`, so it outlives BTCortex's connection and keeps working while a node that keeps running after BTCortex closes keeps its tor). The onion service's private key is kept in the DPAPI vault, so the address stays the same when access is turned off and on again; the tor service publishes registered services again whenever tor starts and lists the server among tor's users. Wallets elsewhere use the usual Electrum port of the network, which tor forwards to the local port.
- **Removal**: the server's settings and configuration go; the index is deleted only on request, and only from a folder carrying BTCortex's marker for that server.
- **Tests**: `tests/integration/electrum.test.ts` runs the whole path with a real regtest bitcoind and the real Fulcrum 2.1.4 from `.test-env` (installed through the real release files), with BTCortex's data under a folder with accented letters.
- **Servers on other computers** (`electrum/remote-electrum-service.ts`, `electrum.remote.*`): electrs, Fulcrum or ElectrumX elsewhere, reached directly or through BTCortex's tor (onion addresses only through it), over TCP or TLS. The line protocol client takes a connection made by the caller (`LineRpcOptions.socket`), so the same probe and address reader run over TLS and SOCKS. A test completes the TLS handshake without trusting the certificate and shows it (subject, issuer, validity, SHA-256 fingerprint, whether Windows' authorities vouch for it for that name); adding a server tests it again and accepts only a publicly trusted certificate or the very one the user accepted, which is then pinned, and every connection checks it before a request is sent. The server's chain is told from its genesis block (`GENESIS_HASHES`); one added for a node must follow the node's chain (`getblockhash 0`). Servers are kept in the settings (`electrum.remote`), checked every minute, raise an alert after five minutes without an answer (at once, critical, when the certificate changed), appear under Remote infrastructure, and answer a node's address lookups in the explorer while the node's own Electrum server is not ready (none set up, still indexing, stopped or failed) — the address view then says which server learnt the address. `apps/orchestrator/src/electrum/remote-electrum.test.ts` (a stand-in server over TCP and TLS with self-signed test certificates in `fixtures/`, pinning, a changed certificate, chains, onion addresses) and `tests/integration/electrum.test.ts` (the real Fulcrum read as such a server, answering the node's address lookups).

## Lightning

BTCortex connects to LND nodes over their REST interface and reads them (specification section 11; research in [`research/notes/lightning.md`](research/notes/lightning.md); user-facing description in [`LIGHTNING_INTEGRATIONS.md`](LIGHTNING_INTEGRATIONS.md)).

- **Client** (`packages/integrations/lnd/src/rest.ts`): HTTPS with the macaroon in `Grpc-Metadata-macaroon`. With a certificate given, it is the only trust anchor and `checkServerIdentity` accepts the presented certificate when its SHA-256 fingerprint equals the given one, whatever host name was used (so onion and LAN addresses work); otherwise only a certificate the given one issued, with the usual name check. Without a certificate the system's authorities apply. Answers are capped at 32 MiB; streaming calls are read line by line. Failures are told apart: unreachable, timeout, certificate, not LND (protocol), and LND's own errors classified as authentication, permission, locked, not found or unavailable.
- **Reading** (`api.ts`): typed parsers turn LND's JSON (64-bit numbers as strings, snake_case) into plain values and drop preimages and payment secrets. **Macaroons** (`macaroon.ts`) are decoded locally (version 2 binary format, LND's `MacaroonId` protobuf) into permissions and an access class. **Local LND** (`local.ts`) is found in `%LOCALAPPDATA%\Lnd`, with `lnd.conf` read but never written; **lndconnect** URIs (`lndconnect.ts`) are parsed and the gRPC port refused.
- **Onion addresses** go through BTCortex's tor: `packages/integrations/tor/src/socks.ts` is a SOCKS5 client (RFC 1928 and RFC 1929) that hands names to tor unresolved and uses a per-connection user name for tor's `IsolateSOCKSAuth`.
- **Service** (`apps/orchestrator/src/lightning/lightning-service.ts`): connections in the settings table (name, address, pinned certificate, macaroon summary, last channel backup) with the macaroon itself in the DPAPI vault; a new connection is probed (`/v1/state`, `/v1/getinfo`) before it is saved; every connection is checked every 30 seconds and `lightning.status` events are published on change; the dashboard reads eleven endpoints in parallel and lists parts the macaroon does not allow; warnings are worked out from what the node reports; channel backups are written with `wx` into `backups\lightning\<connection>\`. The catalogue's `lnd` entry is backed by `lndAdapter`.
- **Installer** (`release.ts`): the release manifest's signatures are separate binary files, so the shared installer accepts several signature files (`signatureUrls`) and binary OpenPGP signatures, counting each primary key once; the threshold is LND's own (5 of the 16 keys in `verify-install.sh`).
- **Tests**: `tests/integration/lightning.test.ts` with three real LND 0.21.4 nodes on regtest (see `tests/integration/support/lnd-node.ts`).

## Payments & merchants

BTCPay Server installations BTCortex connects to (`apps/orchestrator/src/payments/`, `payments.*` methods, `packages/integrations/btcpay`; specification section 13). BTCPay Server runs on Linux, usually in Docker, so BTCortex connects to one rather than installing it.

- **Greenfield client** (`greenfield.ts`): GET requests only, the API key as `Authorization: token <key>`, certificates validated against the system's authorities, the server's own base path kept, redirects refused (an address must be the one BTCPay answers at), answers above 4 MiB refused, every answer checked against the shapes of the published OpenAPI document, and onion addresses reached through a connection opened by BTCortex's tor (application SOCKS port, a stream-isolation name per server).
- **Connecting** (`payments.add`): the address must be `https://`, or plain `http://` only on the local network or to an onion service through Tor, without user name or password. Health, server information and the list of stores are read with the key before anything is kept; the key then goes into the DPAPI vault and only its id into the settings (`payments.servers`). BTCPay's own form for creating a key with exactly `btcpay.store.canviewstoresettings`, `btcpay.store.canviewinvoices` and `btcpay.store.canviewwallet` is offered as a link (`btcpayAuthorizeUrl`); none of them can spend, refund or change a store, and `btcpay.store.canuselightningnode`, which could pay, is never asked for.
- **Checks**: every server once a minute (health, then server information): online, synchronising (with each chain's indexed and tip heights), not answering, or key refused. The monitoring warns when one stays unavailable for 5 minutes and shows payments among the services once a server is connected.
- **Stores** (`payments.dashboard`, kept for a minute): for up to 20 stores, the payment methods, the on-chain balance when that method is enabled, and up to 500 invoices of the last 30 days, counted by status, with settled amounts added up exactly per currency and the ten most recent listed. What the key may not read is reported as such.
- **Tests**: `packages/integrations/btcpay/src/greenfield.test.ts` (a local stand-in server), `apps/orchestrator/src/payments/payments.test.ts`, the payment alerts in `apps/orchestrator/src/monitoring/monitoring.test.ts`, and `apps/desktop/src/features/payments/payments.test.tsx`.

## Backups

The backup centre (`apps/orchestrator/src/backups/`, `backups.*` methods; specification section 22; user documentation in [`BACKUP_AND_RECOVERY.md`](BACKUP_AND_RECOVERY.md)).

- **Inventory** (`BackupService.inventory`): BTCortex's settings and node profiles, each local node's `bitcoin.conf`, the wallets loaded in each running local node (`listwallets`), their public descriptors when they are descriptor wallets (`getwalletinfo`), each Lightning connection's channel backup, and the vault's credentials, each with its kind and whether it holds secrets. Blockchain data, indexes, seeds and the wallets of the Electrum copy BTCortex installed (with their folder) are listed as left out.
- **Collecting**: wallets through `backupwallet` into BTCortex's temporary folder (read and deleted at once), so Bitcoin Core makes the copy consistently; descriptors through `listdescriptors false`; `bitcoin.conf` read directly and, without encryption, masked with `maskSecrets` from `packages/bitcoin-config`; channel backups exported fresh from LND (`LightningService.channelBackup`); credentials revealed from the vault (the scheduled-backup passphrase itself excluded).
- **Format** (`archive.ts`): a folder `BTCortex-backup-<time>` with `manifest.json` (Zod-validated on reading), `README.txt` and `items\`. Encryption is AES-256-GCM per file with a fresh 12-byte nonce, under a 32-byte key from scrypt (N = 2^17, r = 8, p = 1, 16-byte salt); a known text encrypted with the key distinguishes a wrong passphrase from damage. The manifest records stored and original SHA-256 of every file; paths in it must lie under `items/` and are resolved inside the backup folder, so a crafted manifest cannot point elsewhere. A backup is written into `<folder>.partial` with `wx` writes and renamed into place, so an interrupted backup leaves nothing that looks complete.
- **Jobs**: backups and restores run one at a time as `backup.create` and `backup.restore` jobs; the result of the last of each is kept in the settings. A new backup is verified at once, then the retention deletes the oldest folders with a valid BTCortex manifest beyond the number to keep.
- **Schedule**: checked every ten minutes while the orchestrator runs; a backup is due when the last one is older than the interval. A passphrase for encrypted scheduled backups is kept in the DPAPI vault.
- **Restoring**: a managed node's `bitcoin.conf` through `NodeConfigService.save` (all its checks; settings that need confirmation are accepted by the restore's own confirmation; validation details, which may quote secret lines, are reduced to a count), and wallets through `restorewallet` into a running local node, under a new name when the name is taken.
- **Tests**: `apps/orchestrator/src/backups/archive.test.ts` (format, encryption, tampering, wrong passphrase, crafted manifests, retention, interrupted writes) and `tests/integration/backups.test.ts` against a real managed regtest node (wallet copies by Bitcoin Core, encrypted backup verified, `bitcoin.conf` and a wallet restored).

## Deployment profiles

One-click combinations of what BTCortex can set up (`apps/orchestrator/src/profiles/`, `profiles.*` methods; specification section 18).

- **Catalogue** (`catalogue.ts`): profiles A to H with their parts, each part marked as installed by BTCortex, built into BTCortex, to be chosen afterwards (a backup folder) or not available yet. The Lightning and merchant profiles are listed with the reason they cannot be deployed (BTCortex does not install LND; BTCPay Server needs Docker or Linux), and the maximum profile shows those parts as missing rather than leaving them out.
- **Plan** (`plan.ts`, pure): for the user's choices — network, a new node or one BTCortex already has, optional parts, Tor mode, onion service and private broadcasting — the steps in order, the downloads with the release and archive size the publisher's server reports (`releases.ts`: the same "latest version" look-ups the Installed software page uses, then a HEAD request, kept for an hour), storage from the same chain and index estimates as the node set-up (or the Electrum server's own plan for an existing node), memory from the caches BTCortex configures plus a 2 GiB allowance, processors, ports and who can reach them, dependencies, warnings and blockers, privacy and security implications, resource impact, and whether Docker or WSL2 would be needed (never, for the profiles BTCortex deploys).
- **Deployment** (`profile-service.ts`): a `profile.deploy` job that runs the existing set-ups one after the other and waits for each (`JobManager.waitFor`), passing their progress on: the node (`SetupService.start`, without chaining the Electrum server itself), the Electrum server (before Tor, because its set-up needs the node answering), Tor (install, start, then `PrivacyService.configure`, which restarts the node), Sparrow (without consent to replace a server the user chose: that becomes a step needing the user), HWI and Trezor Suite. A failed node stops the deployment; any other failed step leaves the rest in place. Each step's outcome and where to finish it is kept in a deployment record (settings key `profiles`, ten kept); a deployment interrupted by closing BTCortex is marked as such at the next start. Only one deployment runs at a time; `profiles.deploy` is a dangerous method and needs the user's confirmation.
- **Tests**: `apps/orchestrator/src/profiles/profiles.test.ts` (plans for large and small disks, existing nodes, Tor, unavailable profiles; deployment order, consent, failure and interruption; release-size caching; waiting for jobs) and `apps/desktop/src/features/profiles/profiles.test.tsx`.

## Monitoring

Health, alerts and metrics (`apps/orchestrator/src/monitoring/`, `monitoring.*` methods, `alerts.changed` events; specification section 19).

- **Checks** (`MonitoringService`, every 30 seconds): the states of nodes, tor, Electrum servers, Lightning connections and backups, the free space of every disk BTCortex keeps data on, memory and processor use, and the security-relevant settings of each node's `bitcoin.conf` become a health summary and a list of conditions. A condition becomes an alert in the `alerts` table (migration 3), raised once and resolved when it no longer holds. Conditions that can pass by themselves must last first: a node not answering 2 minutes, a mainnet node without peers 10 minutes, a Lightning node or a BTCPay Server unavailable 5 minutes, memory or processor use above the chosen level 10 minutes. Other rules: a node stopped unexpectedly, refusing BTCortex's credentials or stuck for 30 minutes during synchronisation; low disk space (10 GiB warning and 2 GiB critical unless changed); tor or an Electrum server failed; a macaroon expiring within 7 days or an LND certificate within 30; a failed or overdue backup.
- **Changes to `bitcoin.conf`** (`config-watch.ts`): for every node with files on this computer, the effective values of settings that expose the node, run commands, hold credentials or change how it connects (`rpcallowip`, `rpcbind`, `blocknotify`, `rpcauth`, `proxy`, `onlynet` and others) are remembered as HMAC-SHA256 digests under a key kept in the DPAPI vault, never as values, since some hold passwords. A file is compared once it has stayed the same between two checks. A change saved through BTCortex (`NodeConfigService` calls back after writing) is an information alert; one made elsewhere is a warning. New values are shown only for addresses and switches, never for commands or credentials. These alerts report something that happened rather than a lasting condition (`clearsWhenSeen`), so dismissing one resolves it.
- **Metrics** (`metric_samples`, once a minute): processor and memory use from Node's `os` module; the busiest disk's busy time, disk reads and writes and network traffic of the whole computer from Windows' cumulative performance counters (`Win32_PerfRawData_PerfDisk_PhysicalDisk`, `Win32_PerfRawData_Tcpip_NetworkInterface`, read through PowerShell without administrator rights, 64-bit values compared as big integers, so each value is the average over the minute); and for every running node its peers, mempool transactions and size, verification progress and traffic with peers (growth of `getnettotals` between snapshots). Minute samples are folded into hourly averages after a chosen time (48 hours by default) and hourly averages dropped after another (90 days by default); series of removed nodes are dropped.
- **Recent errors**: a log sink keeps the error entries of the last 24 hours (at most 200), already redacted.
- **Exports**: `monitoring.export` writes the chosen series side by side as CSV, or a plain-text report (health, open alerts, alerts of the period, minimum, average and maximum of every series, recent errors), to `…\exports` as `btcortex-monitoring-*`; the 20 newest are kept. CSV fields a spreadsheet would run as formulas are written as text. The interface can only ask File Explorer to show such a file.
- **Interface** (`apps/desktop/src/features/monitoring/`): the health and alert cards on the overview and the monitoring page, a status-bar bell, toasts for new warnings and critical alerts and Windows notifications through `tauri-plugin-notification`, as far as the user's setting allows. The history shows up to four metrics as small multiples on one time scale, lines broken where nothing was measured, long series reduced to about one point per pixel (largest-triangle-three-buckets), each with a table view.
- **Tests**: `apps/orchestrator/src/monitoring/monitoring.test.ts` (alert rules and grace periods, thresholds, sampling and rates, retention, exports, `bitcoin.conf` changes without stored values) and `apps/desktop/src/features/monitoring/monitoring.test.tsx`.

## Developer tools

The developer area (`apps/orchestrator/src/devtools/devtools-service.ts`, `devtools.*` methods; specification section 15). Raw transactions and scripts are decoded by the explorer's methods (`explorer.decodeRaw` also asks `testmempoolaccept`, never broadcasting); PSBTs go through `decodepsbt` and `analyzepsbt` (base64, or hexadecimal converted to base64) and are summed up — inputs with the coins they spend, signatures and what is still missing, outputs, fee, estimated size and fee rate, the next role — with the node's own answer kept for inspection. Descriptors go through `getdescriptorinfo` and `deriveaddresses` (at most 100 addresses); descriptors holding extended or WIF private keys are refused before they reach the node or a log. Protocol features come from `getnetworkinfo` (version, `localservicesnames`), `getdeploymentinfo`, `getindexinfo`, `getchainstates` and the node's `bitcoin.conf` where it is on this computer, each placed in one of the specification's categories — consensus, relay policy, wallet policy, implementation-specific, experimental — with the version that brought it, from docs/research/notes/full-nodes-core.md §9; Bitcoin Knots is recognised and not credited with Core-only features. Blocks are generated on regtest only (`generatetoaddress`, or `generatetodescriptor` to an anyone-can-spend `raw(51)` output). Endpoint probes resolve the name, connect directly or through BTCortex's tor (onion addresses only through tor), check TLS with full certificate validation, and ask the service itself: an HTTP status line, Electrum's `server.version`, or Bitcoin Core's RPC without credentials (a 401 answer). Unit conversions run in the window. ZMQ notifications are read by BTCortex's own ZMTP 3 subscriber (`packages/integrations/bitcoin-core/src/node/zmq.ts`: greeting, NULL mechanism, READY, ZMTP 3.0 subscriptions, multipart frames, no native library); `ZmqWatchService` subscribes to the addresses `getzmqnotifications` reports (raw blocks and transactions only when no hashes are published, `0.0.0.0` publishers reached at the node's host), counts gaps in the publisher's sequence numbers, and publishes `zmq.events` batches of at most 50 events about once a second; watching ends when the tab closes, the publisher goes away, or after 30 minutes. Tests: `apps/orchestrator/src/devtools/devtools.test.ts`, `packages/integrations/bitcoin-core/src/node/zmq.test.ts`, `tests/integration/devtools.test.ts` and `tests/integration/zmq.test.ts` (real bitcoind 31.1 and its libzmq), `apps/desktop/src/features/developer/*.test.ts(x)`.

## Transaction tools

Specification section 14, next to the developer tools. Analysis runs in the window on what the node decoded; everything that needs the node goes through `apps/orchestrator/src/devtools/transaction-tools.ts`; nothing signs.

- **What a transaction means** (`apps/desktop/src/lib/transaction-analysis.ts`, `lib/script.ts`): the lock time as a height or a time and whether it binds (some input not final); each input's sequence for BIP 125 signalling and BIP 68 relative locks (version 2 and later, disable and type flags); what each input spends, from the type of the coin's script when the node knows it, otherwise from the input's shape (a Taproot script path is taken from the shape only with tapscript's leaf version); signatures as strict DER (BIP 66) or BIP 340 with their sighash types, keys, the redeem, witness or tapscript script, and Taproot's annex and control block (leaf version, internal key, depth) as BIP 341 lays them out; base and witness bytes and the discount; outputs below Bitcoin Core's dust limit (its `GetDustThreshold` at the default 3 sat/vB) and OP_RETURN data. Scripts are disassembled for display, with legacy and tapscript multisig (BIP 387 `multi_a`) and the timelocks of `OP_CHECKLOCKTIMEVERIFY` and `OP_CHECKSEQUENCEVERIFY` named. Whether the node replaces unsignalled transactions follows its implementation and version (full RBF in Bitcoin Core since 28.0; Bitcoin Knots by its `-mempoolreplacement`). Shown in the decode tab and in the explorer's transactions; nothing is verified, which stays with the node.
- **Addresses** (`devtools.address`): `validateaddress`, so only the node's network is accepted; the type from the output script's template, and where a bech32 address has mistakes.
- **Payment URIs** (`devtools/bip321.ts`, `devtools.uri.create`, `devtools.uri.read`): BIP 321, the compatible successor of BIP 21 — the scheme and keys in any case, an empty address only with a payment instruction (`lightning`, `lno`, `pay`, `sp`, and on-chain addresses under their human-readable part), decimal BTC amounts (`*digit [. *digit]`, at most eight decimals), `label`, `message`, `amount` and `pop` at most once, and the whole URI refused when a `req-` parameter is not understood. Proof-of-payment callbacks are shown, those with schemes BIP 321 forbids are flagged, and none is ever opened. URIs are made only for addresses the node accepts, with the QR code drawn by the orchestrator (`qrMatrix`).
- **PSBTs**: `devtools.psbt.combine` (`combinepsbt`, for example the signatures of several cosigners) and `devtools.psbt.finalise` (`finalizepsbt`, the transaction given only once every input is complete). The interface combines several PSBTs pasted one per line, and decodes a finished transaction at once.
- **Sending** (`devtools.broadcast`, risk `dangerous`): its parameters require `confirmed: true`; the interface offers it only when `testmempoolaccept` accepted the transaction and asks first, naming the network, the node, the value, the fee and that a transaction cannot be taken back. `sendrawtransaction` keeps Bitcoin Core's limit on absurd fees (`maxfeerate`, 0.10 BTC/kvB by default). The txid is logged, nothing else of the transaction.
- **Following** (`devtools/tracker.ts`, `devtools.track.*`): at most 50 transactions, kept in the settings (`devtools.tracked`), checked every 30 seconds: `getrawtransaction` finds one in the mempool and, with the transaction index, in the chain; otherwise the blocks since following began (from six blocks before) are searched, at most 144 per check. A block reorganised away is searched for again; a transaction that left the mempool and is in no block is reported as such. Sent transactions are followed at once.
- **Coins**: `devtools.output` (`gettxout`, mempool included) and `devtools.scan` (`scantxoutset` over `addr()` descriptors made from validated addresses, or public descriptors; private keys refused before the node sees them; ten minutes allowed, `devtools.scan.abort` stops it), with `estimatesmartfee` for 2, 6 and 144 blocks, or example rates said to be examples. The window weighs each coin with `lib/transaction-size.ts` (BIP 141 weights at the usual sizes: P2PKH 148 vB, P2SH-P2WPKH 91, P2WPKH 68, P2TR key path 57.5): its cost to spend at each rate, dust, coinbase outputs below 100 confirmations, coins that share an address, and what spending them all together would cost. The same weights size a transaction from its inputs and outputs in the convert tab.
- **Tests**: `apps/desktop/src/lib/script.test.ts`, `transaction-analysis.test.ts`, `transaction-size.test.ts`, `apps/desktop/src/features/developer/*.test.tsx`, `apps/orchestrator/src/devtools/bip321.test.ts`, `transaction-tools.test.ts`, `tracker.test.ts` (mempool, blocks without the index, the index, a reorganisation, persistence) and `tests/integration/transaction-tools.test.ts` (real bitcoind 31.1: addresses and bech32 mistakes, a URI, a wallet-signed PSBT combined with its original and finalised, sent and followed into a block, coins found and looked up).

## Security centre

The security posture in one place (`apps/orchestrator/src/security/security-service.ts`, `security.overview`; specification sections 21 and 24.1).

- **Nodes**: how BTCortex signs in (cookie, or a password sent in clear over the local network); the running version against the research's warning matrix (end of life before 25.0 critical, before 29.0 a warning, 30.0 and 30.1 withdrawn), except for Bitcoin Knots, whose versions number differently; a Bitcoin Knots 29.4.1 or later, which follows a chain Bitcoin Core rejects (BIP110 and a BLAKE2b proof of work; `followsKnotsFork` in the contracts), critical on mainnet and also flagged on the Wallets page; and, for files on this computer, `validateConfig`'s findings (RPC exposed, critical when `rpcallowip` admits every address; REST on; commands run on events; `rpcpassword` in plain text) plus ZMQ publishers bound beyond loopback and router port mapping.
- **Services**: tor's version as the directory authorities rate it; each Electrum server reachable only here or also through Tor; each Lightning connection's macaroon (one that can move funds is a warning) and whether its certificate is pinned; backups; open alerts about changed `bitcoin.conf` settings.
- **Software and secrets**: whether every installed version carries the signatures it needs and has file hashes recorded; how many secrets the DPAPI vault holds.
- **This computer**: Windows Firewall's profiles and the access rules of BTCortex's data folder (accounts other than the user, SYSTEM and administrators), read through PowerShell without administrator rights, with the folder passed in an environment variable; checked at most every ten minutes. Rules for individual programs need administrator rights and are not read.
- **Controls**: the protections BTCortex applies itself, including the two still planned (signed releases, dependency auditing).
- **Tests**: `apps/orchestrator/src/security/security.test.ts` and `apps/desktop/src/features/security/security.test.tsx`.

## Update centre

What can be updated and what staying on the current version means (`apps/orchestrator/src/updates/update-service.ts`, `updates.*` methods; specification sections 23 and 24.1).

- **Checks**: once a day in the background (a first look a minute after start, then every six hours whether a day has passed) and whenever the user asks, the newest final release of every program BTCortex installs is asked from the same official sources as its installation (`InstallationService.checkUpdates`). The answer is kept (settings key `updates`), so the page and the alerts need no network.
- **Programs**: the versions installed, the newest release, its release notes (Bitcoin Core's release page or the project's GitHub release), what an update touches (Bitcoin Core is installed beside the current version; tor and Fulcrum restart on the new version; Sparrow must be closed) and how much it matters for security: for Bitcoin Core the worst version a managed node runs against the version-warning matrix (`nodes/version-risk.ts`, shared with the security centre), for tor its version as the directory authorities rate it. Updating starts the Installed software page's verified `installations.update` job.
- **Nodes**: each node's Bitcoin Core version, the newest installed version it could move to, and what the move changes for good across the major versions it crosses (docs/research/notes/full-nodes-core.md §10.7: no supported downgrade, obfuscated blocks from 28.0, legacy wallets and the coin statistics index from 30.0, the transaction index format from 32.0), with the time of the last successful backup. A move is `nodes.useRuntime`, forward only, after confirmation; nodes BTCortex does not run are shown with their risk and updated where they were installed.
- **Deferring**: an update can be put off for seven days or skipped for that version; a newer release ends either. The monitoring raises an `update.available` alert for every pending update (information, or a warning when it matters for security, which deferring does not silence) linking to the page.
- **BTCortex itself**: its version, and that it does not update itself, because its releases are not yet published with signatures it could verify.
- **Tests**: `apps/orchestrator/src/updates/updates.test.ts`, the update alerts in `apps/orchestrator/src/monitoring/monitoring.test.ts`, and `apps/desktop/src/features/updates/updates.test.tsx`.

## Logs and diagnostics

- **Sources** (`apps/orchestrator/src/logs/log-service.ts`): the orchestrator's structured log (JSON lines), the native shell's log (relayed orchestrator output is skipped, since it is already in the orchestrator's log), tor's notices, each Electrum server's output, and for every node whose files are on this computer its `debug.log` and, for managed nodes, the console output captured while bitcoind starts.
- **Reading** (`log-tail.ts`, `parsers.ts`): the first read of a file takes its last 4 MiB; later reads parse only the bytes appended since, so live viewing (every 2 s) costs almost nothing. A file that shrinks or is replaced is read again from its end. Each format has its own parser: Bitcoin Core's `[warning]`/`[error]` tags, `category:level` tags and older "Error:" wording are recognised, and lines without a time are placed at the time of the line before them and marked as such. Every message and context is redacted before it leaves the orchestrator.
- **Queries** (`logs.read`): sources, least severe level, text, time range and a limit; entries from all sources are merged newest first.
- **Diagnostic bundle** (`apps/orchestrator/src/diagnostics`): a ZIP in `…\exports` with system details, node profiles and status, recent jobs, each node's `bitcoin.conf` with secrets hidden, and the last 5 MiB of each log, all redacted; the user's profile path appears as `%USERPROFILE%` and transaction and block ids in Bitcoin Core's log are hidden. The five newest bundles are kept. The interface can only ask File Explorer to show a bundle that is in the exports folder.

- **Breadcrumbs** (`breadcrumbs.tsx`): pages below a sidebar area (a node and its sections, setting up a node, a catalogue entry, a deployment profile) show their trail as a `nav` landmark with the current page marked.

## Decision record

| Decision                                                            | Rationale                                                                                                                                                                                                                          |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Node.js single executable for the orchestrator (`node --build-sea`) | One signed-able sidecar file; users need no Node.js installation; built-in `node:sqlite` avoids native add-ons                                                                                                                     |
| TypeScript 6.0 rather than 7.0                                      | typescript-eslint 8.72 supports TypeScript below 6.1 only; typed linting is part of the quality gate                                                                                                                               |
| DPAPI in Rust                                                       | DPAPI is a Win32 API without a Node.js binding; the shell already exists and keeps secrets out of the WebView                                                                                                                      |
| Cookie authentication for managed nodes                             | No stored secret; the cookie changes on every start and is re-read after HTTP 401                                                                                                                                                  |
| Portable ZIP instead of the Bitcoin Core installer                  | No elevation, versions side by side, no system-wide URI handler, rollback by switching directories                                                                                                                                 |
| `listen=0` by default                                               | No router port mapping and no Windows Firewall prompt; inbound connectivity becomes an explicit, privacy-labelled choice                                                                                                           |
| OpenPGP.js for signature verification                               | Mature, pure JavaScript, no GnuPG installation needed; it validates keys at signature time (stricter than GnuPG). LGPL-3.0, so it ships as a separate, replaceable `openpgp\openpgp.cjs` beside the orchestrator, with its licence |
| Hash routing                                                        | The packaged application is served from a custom protocol where path-based URLs would not survive a reload                                                                                                                         |
| Shared installation pipeline                                        | Every downloaded component goes through the same verification code, so a fix or an audit applies to all of them                                                                                                                    |
| Sparrow connected by cookie only                                    | Sparrow stores RPC passwords in plain text in its settings file; the cookie needs no stored secret and is re-read by Sparrow                                                                                                       |
| Sparrow's settings changed only while it is closed                  | Sparrow rewrites the whole file when it exits, which would silently undo the change                                                                                                                                                |
| Fulcrum as the local Electrum server                                | The only Electrum server with native, signed Windows releases; electrs and ElectrumX need WSL2 or Docker on Windows                                                                                                                |
| DSA accepted for Fulcrum's pinned key only                          | Its author signs with a DSA-2048 key; the fingerprint is pinned and no other DSA key is accepted                                                                                                                                   |
| Bitcoin Knots only with the user's agreement                        | Since 29.4.1 Knots enforces a hard fork and follows a different chain from Bitcoin Core: it is never a drop-in replacement, so it is set up only on request, in its own folders, and a node never moves between the two            |
